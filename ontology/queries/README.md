# SPARQL-запросы к компетентностным вопросам

Шесть запросов реализуют компетентностные вопросы раздела 1.5 статьи в редакции rev05. Они выполняются над объединённым графом [онтологии](../analytics-core.ttl) и [примера данных](../article-example.ttl). Пример содержит все 484 записи пар: по 22 фактора и 11 показателей для января и июля 2013 года. Файл `cxl-example.ttl` для запросов не требуется. Удалённая SPARQL-служба и разрешение адресов w3id через Интернет не используются.

## Вопросы и результаты

| № | Компетентностный вопрос | Файл | Январь: строк | Июль: строк |
|---|---|---|---:|---:|
| КВ1 | Какие аналитические факторы имеют записи оценки для выбранного показателя? | [cq1_factors.rq](cq1_factors.rq) | 22 | 22 |
| КВ2 | Как ранжируются факторы по определённым значениям ST для выбранного показателя? | [cq2_rank_st.rq](cq2_rank_st.rq) | 22 | 22 |
| КВ3 | Какие факторы имеют модуль CE не ниже границы выраженного эффекта? | [cq3_strong_effects.rq](cq3_strong_effects.rq) | 2 | 2 |
| КВ4 | Какие оценки проходят строгие пороги карты? | [cq4_selected_edges.rq](cq4_selected_edges.rq) | 20 | 16 |
| КВ5 | Согласованы ли категория и статус каждой записи с правилом таблицы 1? | [cq5_classification.rq](cq5_classification.rq) | 242 | 242 |
| КВ6 | Какие результаты и сведения о происхождении доступны для объясняющего отчёта? | [cq6_report.rq](cq6_report.rq) | 242 | 242 |

КВ1-КВ3 по умолчанию используют прибыль (`ex:profit_eur`). В КВ2 первой в обоих периодах стоит рыночная цена электроэнергии, вторым - налог на CO₂. КВ3 возвращает эти же два фактора; граница модуля CE берётся из `ceStrong` правила и равна 0,3. Равенство этой границе включается в КВ3. Знак CE сохраняется. КВ1 включает записи с неопределёнными оценками; КВ2 и КВ3 требуют соответствующее числовое значение, поэтому их число строк для другого показателя может быть меньше.

КВ4 использует строгие пороги карты: ST больше 0,1 и модуль CE больше 0,3. Равенство любому из порогов не проходит отбор. В выборке 20 рёбер для января и 16 для июля; 11 пар общие. Значение `actualEdge` показывает записанное ребро; подходящая оценка остаётся в выдаче и при отсутствии ребра. В КВ6 поля `selected` и `hasEdge` отдельно показывают прохождение условий и фактическое наличие ребра. Вес ребра равен CE с сохранением знака.

## Категории и состояния записи

КВ5 вычисляет категорию по порогам `ex:table1Rule`: `stLow=0.3`, `stHigh=0.7`, `ceLow=0.1`, `ceStrong=0.3`.

| Категория | Условие после проверки состояний записи |
|---|---|
| `Critical` | ST не менее 0,7; модуль CE не менее 0,3 |
| `StrongLowST` | ST больше 0, но меньше 0,3; модуль CE не менее 0,3 |
| `Uncertainty` | ST не менее 0,7; модуль CE меньше 0,3 |
| `Background` | ST меньше 0,7; модуль CE меньше 0,1 |
| `Moderate` | Остальные определённые оценки с положительным ST |

`No_ST` и `undefined` являются состояниями записи, а не категориями таблицы 1. При определённых оценках ST не больше нуля и модуле CE не менее 0,1 состояние `No_ST` проверяется до присвоения категории. Категория для такой записи отсутствует. `undefined` означает отсутствие обоих числовых значений и категории; частично заполненная запись не считается корректной. При неположительном ST и модуле CE меньше 0,1 действует условие `Background`.

В январе имеются 237 классифицированных записей и 5 записей `No_ST`; в июле - 218 классифицированных, 2 `No_ST` и 22 `undefined`. Последние относятся к новым мощностям СЭС, для которых в июльском наборе нулевой масштаб выходного показателя. КВ5 возвращает все записи и проверяет их через `matches`; в сохранённом результате все значения истинны. `computedStatus` отделён от `computed`: во втором поле находится только категория, а для `No_ST` и `undefined` оно не связано.

КВ6 также возвращает все 242 записи периода, включая исключённые и неопределённые, с причиной невключения в карту. Неопределённые значения не заменяются нулями. Отсутствующие сведения о версиях программ, масштабах нормирования, ATE и расчётном контрасте остаются несвязанными.

## Запуск и проверка

Скачайте репозиторий целиком, сохранив структуру каталогов. В отдельном Python-окружении установите использованные версии библиотек:

```sh
python -m pip install rdflib==7.6.0 pyparsing==3.3.2
```

Из корня репозитория выполните:

```sh
python ontology/queries/run_queries.py --check
python ontology/queries/test_queries.py
```

Проверено с Python 3.12.14, RDFLib 7.6.0 и pyparsing 3.3.2. Первая команда сравнивает выдачи обоих периодов с [expected-results.json](expected-results.json); при расхождении возвращается ненулевой код завершения, файл ожидаемых результатов не изменяется. Вторая команда проверяет настоящие SPARQL-запросы на синтетических граничных примерах, переключение периода и отказ при несовпадении с сохранённой выдачей. Эти тестовые значения не являются результатами исследования.

Без `--check` скрипт выводит полный JSON. Для одного периода можно указать `--period january` или `--period july`; по умолчанию используется `--period all`:

```sh
python ontology/queries/run_queries.py --period july --check
python ontology/queries/run_queries.py --period january
```

Сознательное обновление сохранённой выдачи после проверки изменений выполняется отдельной командой:

```sh
python ontology/queries/run_queries.py --write-expected
```

`--write-expected` допускается только для обоих периодов. Его нельзя сочетать с `--check`. Не следует использовать эту команду как замену проверке расхождений.

## Параметры и формат результатов

Отдельные файлы `.rq` имеют январские значения `VALUES`, чтобы их можно было запускать самостоятельно в средстве с поддержкой SPARQL 1.1. Для июля замените ресурс периода:

| Параметр | Январь | Июль |
|---|---|---|
| `experiment` в КВ1, КВ2, КВ3, КВ5 | `ex:italyExperiment` | `ex:italyExperimentJuly` |
| `map` в КВ4 | `ex:demoMap` | `ex:julyMap` |
| `report` в КВ6 | `ex:demoReport` | `ex:julyReport` |

Скрипт заменяет только соответствующий ресурс в блоке `VALUES`, сохраняя показатель и логику запросов. Показатель в КВ1-КВ3 можно изменить в отдельном `VALUES ?indicator`. Классификация использует пороги правила, а отбор рёбер - пороги карты; это разные операции. Январское имя `ex:demoMap` сохранено для совместимости с примером запроса в статье.

JSON имеет поля `schema_version` и `periods`, затем ключ периода (`january`, `july`) и имя запроса. Каждая выдача содержит `variables`, `row_count` и `rows`. Значения RDF-термов записаны в нотации N3 с сохранением типа и языковой метки; `null` означает несвязанную переменную. Порядок строк задаётся `ORDER BY`. При самостоятельном запуске загрузите онтологию и пример в один граф по умолчанию; логический вывод OWL не требуется.

## Границы проверки

Данные представляют сохранённые агрегированные оценки для двух периодов без повторного статистического расчёта. Происхождение и ограничения описаны в [документации онтологии](../README.md). Запросы проверяют представление, извлечение, классификацию и пороговый отбор. Они не рассчитывают индексы Соболя и направленные эффекты, не выполняют проверки DoWhy и не подтверждают причинные предпосылки модели. Исходные строки сценариев DXY в RDF-пример не включены.
